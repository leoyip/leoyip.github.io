Mac 卡顿排查实录：从 load 395 到 5.5

发表于2026-10-22|更新于2026-10-22|技术

一台 2018 款 MacBook Pro，i5 四核、16GB 内存，用了六年。某天早上开机后光标一直在转圈，敲一个字要等两秒。这不是玄学，是可以量化的。本文记录完整排查过程，含所有实测数据和命令。

起因

10 月 21 日早上九点，我发现电脑卡得反常。不是”有点慢”，是打字有延迟、切换应用要等、风扇在转但什么也没干。

第一反应是”重启一下”。但重启前的三分钟等待让我改主意了——与其重启掩盖症状，不如先看看它到底在干什么。事实证明这个决定是对的，因为重启之后一切会恢复正常，症状消失，问题继续潜伏。

同时 pmset -g therm 给出了另一个关键信息：

CPU_Speed_Limit = 26 是说 CPU 只能发挥 26% 的性能。2.3GHz 的 i5 实际跑在 0.6GHz 左右。这就是”卡”最直接的物理原因。

二、数据拼出的三层问题

继续往下挖，三个层次的问题浮出水面。

指标 实测值 正常值 判定
CPU 速度上限 26%~60% 100% 严重降频
系统负载 395 < 4 超载百倍
Spotlight 索引进程 16 个并发 0~2 全量重建中
Time Machine 卡在 Starting 超 6 分钟 正常推进 挂死
内存可用 97 MB > 2 GB 接近耗尽
Page-in 次数 92.3 万（开机 75 分钟） 数万 疯狂读盘
系统盘占用 89% < 80% 偏高

硬件层：CPU 降频。这台 2018 款用了六年，硅脂早干了，风扇积灰，散热能力大幅衰减。CPU 一热就自动降频保护自己。

系统层：Time Machine 正在备份到外接硬盘，但卡在 Starting 阶段出不来。原因是那块备份盘只剩 37GB（已用 93%），装不下这次增量。backupd 卡在死循环里空转，持续抢占磁盘 I/O。与此同时 Spotlight 在做全量重建索引，16 个 mdworker_shared 进程同时啃硬盘。

存储层：系统盘 89% 满，内存只剩 97MB，swap 为 0——系统在靠内存压缩硬撑，92 万次 page-in 就是代价。

三件事叠在一起，CPU 被逼到降频，负载冲到 395。

三、动手：先解决制造麻烦的

诊断清楚后，处理顺序很关键。先停掉”正在制造持续压力”的东西，再谈优化。

第一步，拔掉备份盘。 这一下比什么都管用。backupd 一停，磁盘 I/O 立刻释放，CPU 温度下来，降频自然解除。

效果是立竿见影的：

指标 处置前 拔盘后
系统负载 395 9.0
CPU 速度上限 26% 100%
内存可用 97 MB 130 MB

第二步，管住 Spotlight。 我的 Obsidian 库里有 20GB 代码目录——历史项目、模型权重、数据集、11 个 node_modules。Spotlight 会逐个分析这些文件，但你永远不会在搜索框里搜 .pyc 或模型权重。

四、意外发现：47GB 的风景视频

清理完缓存，磁盘占用反而从 89% 涨到了 90%。这不正常，于是我扫了一遍全盘，发现在这里：

这是 macOS 的航拍屏保资源缓存。从 Sonoma 开始，系统会自动下载 4K HDR 的风景视频用于动态壁纸和屏保，日积月累堆到了 47GB——里面有 150 个 .mov 文件，单个最大 1.4GB。

而这些视频我压根没在看。文件时间戳显示是 2024 年 8 月下载的，两年没动过。

五、一个顺序问题

我当时的方案是”直接删掉这 47GB”。但被问了一句：

屏保那个功能要先关闭再清理数据吧？

这个问题救了 47GB 的下载流量。

查配置确认：

输出显示壁纸和屏保的 Provider 都是 com.apple.wallpaper.choice.aerials——航拍模式还开着。如果这时候直接删缓存，idleassetsd 会发现资源缺失，然后默默把 47GB 全部重新下载回来。

正确顺序是：先在系统设置里把壁纸换成静态图，再删缓存。 删除前检查配置，删除后确认不再自动下载。

六、结果

第二天复核，数据如下：

指标 排查前 处理后
系统负载 395 5.5
CPU 速度上限 26% 100%
磁盘可用 47 GB 107 GB
磁盘占用 90% 77%
内存可用 97 MB 640 MB

磁盘占用降到 77%，进入了 APFS 的健康区间（超过 85% 会明显拖慢写入）。累计释放约 60GB。

七、几条可以复用的经验

1. 卡顿不是感觉，是数据。 load average、pmset -g therm、vm_stat 三个命令就能判断是 CPU、内存还是 I/O 的问题，比反复重启有价值得多。

2. 降频往往是被其他问题逼出来的。 我一开始以为 CPU 老化要清灰，实际上它是被 Time Machine 和索引的高负载加热的。先解决压力源，降频自己就好了。

3. 寻找”正在空转”的进程。 backupd 卡在 Starting、mds 卡在重建——这类”看起来在工作实际没进展”的进程是隐形杀手，tmutil status 和 mdutil -s 能看出来。

4. 删之前先想”它会不会回来”。 缓存类文件大多会自动重建。不先关掉触发它的功能就删除，等于白删。

5. 官方清理命令优于手动删除。 npm cache clean、pip cache purge、brew cleanup 都有内置的清理逻辑，比 rm -rf 安全。

最后

这台 2018 款 MBP 现在运行 macOS 15.7.7，已经超出它的舒适区，但仍能胜任日常文字工作、代码编辑和笔记管理。它慢，但慢的原因大部分不是硬件不行，而是系统里堆积了太多没人管的缓存和索引任务。

顺带一句：处理完之后我发现，这台机器现在一份备份都没有——备份盘拔了、本地快照清了。磁盘腾出来了，但数据安全反而成了新问题。下一件事是接一块 1TB 以上的硬盘重新做 Time Machine。

清理空间是为了用得更久，不是为了清空。这个顺序别搞反。
